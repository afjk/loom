# Loom Specification

## Chapter 1: Design Philosophy

Loom describes relationships, not results.

A Loom graph is a serializable definition of how outputs are derived from an environment.  
The graph itself should be treated as a deterministic relationship: given the same environment and the same evaluation semantics, it should produce the same outputs.

In other words:

same graph + same environment + same evaluation semantics = same output

This principle is the foundation of Loom's design.

### Three-Layer Model

Loom separates behavior into three layers:

1. Graph
2. Environment
3. Runtime

#### Graph

The graph describes relationships between values, events, state, and outputs.

It is data, not host-language code.  
Because the graph is represented as JSON, it can be serialized, transmitted, edited at runtime, generated by AI, visualized as nodes, and executed by different host environments such as Web, Unity, Godot, or other runtimes.

The graph should remain as deterministic and side-effect-free as possible.

#### Environment

The environment contains the external inputs used to evaluate the graph.

The environment includes:

- synchronized time from a shared clock
- input values
- input events

Examples include slider values, button presses, ride start events, player actions, page changes, or any other external signal injected into the graph.

The environment is separate from the graph.

This separation is important: Loom does not need to synchronize every computed result.  
Instead, Loom synchronizes the environment. If every client evaluates the same graph with the same environment, each client can compute the same result independently.

#### Runtime

The runtime evaluates the graph against the environment and applies the resulting outputs to the host system.

The runtime is responsible for:

- evaluating nodes
- preserving deterministic evaluation semantics
- managing explicit state nodes
- applying outputs to the host scene or application
- mapping graph outputs to host-specific APIs such as DOM, Unity Transform, Godot Node, or other runtime targets

Different runtimes may exist for Web, Unity, Godot, or other systems, but they should follow the same evaluation semantics.

### Synchronization Model

Loom synchronizes causes, not continuous results.

Instead of broadcasting object positions, rotations, animation values, or other computed outputs every frame, Loom prefers to synchronize the environment:

- input events are broadcast when they occur
- input values are broadcast when they change
- time is based on a synchronized clock

Continuous behavior is then computed locally by each client.

For example:

- A page-turn event is synchronized; slide animation is computed locally.
- A fire event is synchronized; projectile motion is computed locally.
- A ride-start event is synchronized; vehicle movement is computed locally.
- A button press is synchronized; the resulting behavior is computed locally.

This reduces network traffic and makes behavior easier to replay, debug, and reproduce.

### Determinism Requirements

The environment synchronization model only works if Loom evaluation is deterministic.

Therefore, Loom should follow these rules:

- Pure computation nodes should have no hidden side effects.
- Stateful behavior must be represented explicitly through state nodes.
- State nodes must have stable identifiers.
- Time-dependent behavior should use synchronized time rather than local wall-clock time.
- Evaluation order must be well-defined.
- Host-specific behavior should be isolated at the runtime boundary.
- Non-deterministic or external effects should not be hidden inside ordinary graph nodes.

A more precise form of the core rule is:

same graph + same environment + same evaluation semantics = same output

### State and Side Effects

Most Loom nodes should be pure relationship nodes.

Stateful behavior is allowed, but it must be explicit.  
Examples include delay, previous-value, accumulator, low-pass filter, or state-machine nodes.

Side effects should be isolated at output boundaries.

This means that Loom should distinguish between:

- calculating a value
- producing an output command
- applying that command to a host scene

The graph describes what should happen.  
The runtime decides how to apply it to the host environment.

### Result Synchronization as a Fallback

Not everything should be forced into Loom's deterministic model.

Some behavior may depend on host-specific systems, physics engines, external services, AI generation, random sources, device-specific data, or other non-deterministic processes.

For those cases, SceneSync or another host synchronization layer may synchronize results directly.

In practice, Loom and SceneSync can use a two-mode synchronization strategy:

1. Environment synchronization for deterministic Loom behavior
2. Result synchronization for host-specific or non-deterministic behavior

Loom should be used for behavior that can be described as deterministic relationships.  
SceneSync should handle behavior that must be synchronized as external results.

### Summary

Loom is a serializable behavior graph system inspired by Arrowized FRP.

It describes relationships as JSON, keeps the environment separate, synchronizes that environment across clients, and lets each runtime compute the results independently.

Loom's role is to describe synchronized behavior.  
SceneSync's role is to synchronize the environment and, when necessary, synchronize external results.

For background concepts and related systems such as Arrowized FRP and Yampa, see Appendix A: Influences.

## Chapter 1: Design Philosophy (日本語版)

Loom は関係を記述する。結果ではなく。

Loom グラフは、環境から出力がどのように導き出されるかを説明する直列化可能な定義です。
グラフ自体は決定的な関係として扱うべきです。同じ環境と同じ評価セマンティクスが与えられれば、同じ出力を生成するはずです。

言い換えれば：

同じグラフ＋同じ環境＋同じ評価セマンティクス＝同じ出力

この原則が Loom の設計の基礎です。

### 三層モデル

Loom は動作を 3 つのレイヤーに分離します：

1. グラフ
2. 環境
3. ランタイム

#### グラフ

グラフは、値、イベント、状態、出力の間の関係を記述します。

これはホスト言語コードではなく、データです。
グラフは JSON として表現されるため、直列化・送信・実行時編集・AI 生成・ノード可視化が可能であり、Web、Unity、Godot、またはその他のランタイムなど異なるホスト環境で実行できます。

グラフは可能な限り決定的で、副作用のない状態を保つべきです。

#### 環境

環境は、グラフを評価するために使用される外部入力を含みます。

環境には以下が含まれます：

- 共有クロックからの同期化された時刻
- 入力値
- 入力イベント

例としては、スライダー値、ボタン押下、乗車開始イベント、プレイアー操作、ページ変更、またはグラフに注入されるその他の外部信号があります。

環境はグラフとは分離されています。

この分離は重要です。Loom は計算結果をすべて同期する必要がありません。
代わりに、Loom は環境を同期します。すべてのクライアントが同じグラフを同じ環境で評価すれば、各クライアントは独立して同じ結果を計算できます。

#### ランタイム

ランタイムはグラフを環境に対して評価し、結果の出力をホストシステムに適用します。

ランタイムは以下の責任があります：

- ノードを評価する
- 決定的な評価セマンティクスを保持する
- 明示的な状態ノードを管理する
- ホストシーンまたはアプリケーションに出力を適用する
- グラフ出力を DOM、Unity Transform、Godot Node、またはその他のランタイム対象のようなホスト固有 API にマッピングする

異なるランタイムが Web、Unity、Godot、またはその他のシステム用に存在する可能性がありますが、同じ評価セマンティクスに従うべきです。

### 同期モデル

Loom は原因を同期します。継続的な結果ではなく。

オブジェクトの位置、回転、アニメーション値、またはその他の計算出力を毎フレーム送信する代わりに、Loom は環境を同期することを推奨します：

- 入力イベントは発生時に送信される
- 入力値は変更時に送信される
- 時刻は同期クロックに基づいている

継続的な動作は、その後、各クライアントで局所的に計算されます。

例：

- ページターンイベントは同期されます。スライドアニメーションは局所的に計算されます。
- 発火イベントは同期されます。発射体モーションは局所的に計算されます。
- 乗車開始イベントは同期されます。乗り物の移動は局所的に計算されます。
- ボタン押下は同期されます。結果の動作は局所的に計算されます。

これにより、ネットワークトラフィックが削減され、動作の再生、デバッグ、再現が容易になります。

### 決定性の要件

環境同期モデルは、Loom の評価が決定的である場合にのみ機能します。

したがって、Loom は以下のルールに従うべきです：

- 純粋な計算ノードは、隠れた副作用を持つべきではありません。
- ステートフルな動作は、状態ノードを通じて明示的に表現される必要があります。
- 状態ノードは安定したID を持つ必要があります。
- 時間依存の動作は、ローカルウォールクロック時間ではなく、同期時刻を使用する必要があります。
- 評価順序は十分に定義される必要があります。
- ホスト固有の動作は、ランタイム境界で分離される必要があります。
- 非決定的または外部の効果は、通常のグラフノード内に隠されるべきではありません。

コアルールのより正確な形式は：

同じグラフ＋同じ環境＋同じ評価セマンティクス＝同じ出力

### 状態と副作用

ほとんどの Loom ノードは、純粋な関係ノードであるべきです。

ステートフルな動作は許可されていますが、明示的である必要があります。
例としては、遅延、前の値、アキュムレータ、ローパスフィルタ、または状態マシンノードがあります。

副作用は出力境界で分離される必要があります。

これは、Loom が以下を区別する必要があることを意味します：

- 値を計算する
- 出力コマンドを生成する
- そのコマンドをホストシーンに適用する

グラフは何が起こるべきかを記述します。
ランタイムは、それをホスト環境にどのように適用するかを決定します。

### フォールバックとしての結果同期

すべてを Loom の決定的モデルに強制すべきではありません。

一部の動作は、ホスト固有システム、物理エンジン、外部サービス、AI 生成、ランダムソース、デバイス固有データ、またはその他の非決定的なプロセスに依存する可能性があります。

これらの場合、SceneSync または別のホスト同期レイヤーは、結果を直接同期できます。

実際には、Loom と SceneSync は 2 つのモード同期戦略を使用できます：

1. 決定的な Loom 動作の環境同期
2. ホスト固有または非決定的な動作の結果同期

Loom は、決定的な関係として説明できる動作に使用される必要があります。
SceneSync は、外部結果として同期する必要がある動作を処理する必要があります。

### まとめ

Loom は、Arrowized FRP に触発された直列化可能な動作グラフシステムです。

JSON として関係を記述し、環境を分離したままにし、その環境をクライアント全体で同期し、各ランタイムが結果を独立して計算できるようにします。

Loom の役割は、同期化された動作を記述することです。
SceneSync の役割は、環境を同期し、必要に応じて外部結果を同期することです。

背景概念および Arrowized FRP や Yampa などの関連システムについては、「付録 A: 影響」を参照してください。

## Chapter 2: Overview

Loom は、ブラウザで動く**ステートレスなデータフロー実行エンジン**です。JSON でグラフを定義し、毎フレーム値を計算・更新します。

**英語での一行説明：**
> A stateless dataflow engine for the browser. Build reactive visual, audio, and 3D content by composing pure functions.

**日本語での説明：**

ブラウザで動くステートレスなデータフロー実行エンジン。純粋な関数の合成により、リアクティブな視覚・音響・3D コンテンツを構築します。

Loom の核は、以下の仕組みです：

1. グラフ状に配置された複数の「ノード」を定義（JSON で記述）
2. ノードどうしを「エッジ」で接続（値の流れを表現）
3. エンジンが毎フレーム、グラフを評価し、各ノードの出力値を計算
4. 外部から `engine.getValue()` で任意のノードの出力値を取得し、画面や音響に反映

## Chapter 3: Design Principles

### 原則 1：ステートレスを基本とする

状態（過去を引きずる値）を持たず、現在時刻と入力だけから出力が決まる純粋なデータフローを基盤とします。

**意図：**
- 任意のタイミングで同じ計算を再実行しても、同じ結果が得られる
- 記録と再生が容易
- マルチプレイの同期が単純

### 原則 2：状態が必要な部分は明示的に局在化する

「状態部品」という限定された種類の部品にだけ状態を持たせ、グラフ上で目に見える形で管理します。

**意図：**
- 状態を持つ部品がどこかは常に明確
- デバッグやテストが容易
- 状態管理の責任が明確に分離される

### 原則 3：副作用を出口側に集める

外部への副作用（位置や色を変える、音を鳴らす、メッセージを送るなど）は「シンク」専用部品でのみ行います。中間の計算は副作用を持ちません。

**意図：**
- 中間の計算ロジックが純粋で、テスト・再利用が容易
- 副作用がどこで起きるかが明確
- グラフの再利用性が高い

### 原則 4：テキスト表現とビジュアル表現の二重持ち

内部はテキストの専用記法（DSL）で持ち、UI はそれを視覚化します。両方向に変換可能で、人間も AI も自由に行き来できます。

**注意：** 第ゼロ段階では DSL とビジュアル UI は実装せず、JSON 直書きから始めます。

**意図：**
- テキスト形式により、バージョン管理・AI 処理が容易
- ビジュアル UI により、直感的な編集が可能
- 両者の変換が可能なため、ツール化が容易

## Chapter 4: Data Flow Model

### 4.1 値の二種類

すべての値は次のどちらかに分類されます。

**連続値（Behavior）**

常に何らかの値が流れている「川」のようなもの。時間的に途切れません。例：

- 時計（経過時間）
- Sin 波（周期的な振動）
- 温度センサーの現在値
- マウスのポインタ位置

第ゼロ段階では、連続値のみを扱います。

**イベント（Event）**

時々瞬間的に発生する「雷」のようなもの。時間的に離散的です。例：

- クリック
- キープレス
- メッセージ受信
- 閾値超え（値が特定の値を越えたとき）

イベントは第一段階で導入します。

### 4.2 ノード（部品）の 5 カテゴリ

部品は次の 5 つのカテゴリに分かれます。

#### ソース部品

入力なしで値を生み出すノード。

**例：** `clock`（時刻）、`constant`（定数）

#### 入力部品

外界から値を受け取るノード。ユーザーの操作やネットワーク通信などが対象。

**例：** `pointerPosition`（マウス位置）、`pointerClick`（クリック）、`webhook`（HTTP リクエスト）

バージョン 0.3.0 では `smoothLerp`、`lowpass`、`delay1`、`integrate` を実装済み。

#### 変換部品

純粋な計算で値を変換する。状態を持ちません。

**例：** `add`（足し算）、`multiply`（掛け算）、`sine`（正弦波）、`map`（配列変換）

#### 状態部品

内部に状態を持つ唯一のカテゴリ。過去の値を記憶し、それに基づいて出力を決定します。

**例：** `accum`（積分）、`smooth`（なめらか化）、`delay`（遅延）

第ゼロ段階では実装されません。

#### シンク部品

外部への副作用を持つノード。値を受け取り、画面・音響・ネットワークなどに影響を与えます。

**例：** `setPosition`（位置変更）、`playSound`（音声再生）、`broadcastEvent`（イベント送信）

第ゼロ段階では実装されません。

### 4.3 イベントの伝播モデル

- イベントは「あるフレームで発生／発生しない」のいずれかの状態を持つ
- ノードの Event 型入力ポートは、未接続またはそのフレームに上流からイベントが届かなかった場合「発生していない」扱い
- ノードの evaluate 関数は毎フレーム呼ばれるが、Event 型出力ポートに値を書くかどうかはノード自身の判断
- 同一フレーム内で複数のイベントが同じ Event 型ポートに到達することがあり得る。その場合、下流ノードは配列としてすべて受け取れる
- イベントはフレームをまたがない。次フレームでは新たに発生したイベントだけが下流に流れる

### 4.4 接続の型ルール

- Behavior 型ポート → Behavior 型ポート：許容（既存通り）
- Event 型ポート → Event 型ポート：許容
- Behavior ↔ Event のクロス接続：禁止、`TYPE_MISMATCH` エラー
- ペイロード型が異なる場合（例：`event<vec2>` → `event<void>`）も `TYPE_MISMATCH` エラー

**例外：** `sample` ノードの `value` 入力ポート（Behavior 型）には Event 型の上流から接続することが許される唯一のケース。これは Behavior 値をイベントトリガでサンプリングするための設計である。

### Phase Zero Scope

#### 実装外（第二段階以降）

- ❌ DSL とパーサ
- ❌ ビジュアルエディタ
- ❌ マルチクライアント同期
- ❌ Three.js アダプタ

## Chapter 6: Node Specifications

### ノード型のメタデータ構造

各ノード型は、内部的に以下のメタデータを持つオブジェクトとして定義されます。

```javascript
{
  category: "source" | "transform" | "state" | "sink" | "input",
  inputs: [
    { name: "t", type: "number", default: 0 },
    ...
  ],
  outputs: [
    { name: "out", type: "number" }
  ],
  params: [
    { name: "freq", type: "number", default: 1 },
    ...
  ],
  evaluate: (inputs, params, ctx) => outputs
}
```

このメタデータは以下の目的で利用されます。

- グラフ読み込み時の検証（未知のポートやパラメータの検出）
- エラーメッセージの生成（どのノードのどのポートが問題かを特定）
- 将来のビジュアルエディタでの自動 UI 生成
- 将来の AI 連携でのスキーマ提供

### 6.0 入力・パラメータの統一ルール

すべてのノードは、入力ポートとパラメータについて次の優先順位で値を決定します。

1. 入力ポートにエッジが接続されていれば、その値を使う
2. エッジが接続されていなければ、`params` の同名フィールドの値を使う
3. それも指定されていなければ、ノード型ごとのデフォルト値を使う

このルールにより、すべてのノードの設定値は「グラフ上で動的に変えたければエッジで接続、静的に固定したければ `params` で指定」という形で統一的に扱えます。

### 6.1 clock

**カテゴリ：** ソース部品

**入力：** なし

**出力：**
- `t`（経過秒、エンジン起動時を 0 とする）
  - 型：`number`（double）

**パラメータ：** なし

**説明：**

エンジン起動からの経過時間（秒）を常に出力します。

**例：**
```json
{
  "id": "timer",
  "type": "clock"
}
```

### 6.2 constant

**カテゴリ：** ソース部品

**入力：** なし

**出力：**
- `out`（定数値）
  - 型：`number`（デフォルト 0）

**パラメータ：**
- `value`（出力する定数値、型：`number`、デフォルト 0）

**説明：**

パラメータで指定した定数値を常に出力します。変わりません。

**例：**
```json
{
  "id": "freq_source",
  "type": "constant",
  "params": {
    "value": 2.5
  }
}
```

### 6.3 sine

**カテゴリ：** 変換部品

**入力：**
- `t`（時刻、未接続時は `0`）
  - 型：`number`
- `freq`（周波数、Hz、未接続時は `params.freq`、デフォルト 1）
  - 型：`number`
- `amplitude`（振幅、未接続時は `params.amplitude`、デフォルト 1）
  - 型：`number`
- `phase`（位相、ラジアン、未接続時は `params.phase`、デフォルト 0）
  - 型：`number`
- `offset`（オフセット、未接続時は `params.offset`、デフォルト 0）
  - 型：`number`

**出力：**
- `out`（正弦波出力）
  - 型：`number`
  - 計算式：`sin(t * freq * 2π + phase) * amplitude + offset`

**パラメータ：**
- `freq`（周波数、Hz、型：`number`、デフォルト 1）
- `amplitude`（振幅、型：`number`、デフォルト 1）
- `phase`（位相、ラジアン、型：`number`、デフォルト 0）
- `offset`（オフセット、型：`number`、デフォルト 0）

**説明：**

時刻 `t` を入力として、正弦波を計算します。周波数、振幅、位相、オフセットでカスタマイズ可能です。

**例：**
```json
{
  "id": "oscillator",
  "type": "sine",
  "params": {
    "freq": 2.0,
    "amplitude": 1.5,
    "phase": 0,
    "offset": 0
  }
}
```
